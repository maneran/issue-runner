Work through every open issue that is unlabeled or labelled `needs-triage`
(`gh issue list --repo {{repo}} --state open --json number,title,body,labels,comments`), oldest first.
For each one:

1. Category: `bug` or `enhancement`.
2. State: `ready-for-agent` if an agent could implement it from the thread plus a brief; `needs-info`
   if the reporter must answer something (post the question); `ready-for-human` if it needs a decision,
   credentials, or product judgment; `wontfix` only when the repo's docs say the behaviour is intended.
3. Priority: `P0` (broken for users now), `P1` (important), `P2` (default). Say why in one line.
4. Size: `size:S` (one file), `size:M` (a few files), `size:L` (cross-cutting or more than one session).
5. If `size:L` and `ready-for-agent`: split it. Open 2-5 sub-issues, each `size:S` or `size:M`, each with
   its own brief, linked as sub-issues of the parent (`gh api` sub-issues endpoint; fall back to a task
   list in the parent body plus `Part of #<n>` at the top of each child). The parent gets `agent:hold` so the runner never picks it whole, and the
   children get `ready-for-agent`. If you cannot find a clean split, label the parent `ready-for-human`
   and say what blocks the split.
6. When you set `ready-for-agent`, post an agent brief as a comment: the behaviour to build, the
   acceptance criteria as checkable statements, what is out of scope. No file paths or line numbers;
   they go stale.

Apply labels with `gh issue edit`. Remove `needs-triage` once a state label is set. Never change a
state label a human already set; if the current labels conflict, leave them and note it in the moves file.

When done, write `triage-moves.json` in the working directory: a JSON list of
`{"number": <issue>, "move": "<one line: labels set and why>"}`, one entry per issue you touched.
